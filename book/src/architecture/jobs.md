# Job lifecycle

A **job** is one task: one host, one expected state, Assess or Reach. Its id
is the task's idempotency key:

| Origin | Key |
|---|---|
| run now | `run:{command_id}:{host_id}` |
| recurring order | `rec:{order_id}:{order_revision}:{slot}:{host_id}` |
| regops pass | generated by regops, reused on retries |

## States

```text
PENDING ──▶ STARTED ──▶ FINISHED
   │           │
   │           └──▶ ABORT_REQUIRED ──▶ ABORTED
   ├──▶ EXPIRED   (waited longer than its slot)
   └──▶ FAILED    (kept failing, dead-lettered)
```

- States only move forward: events may arrive in any order and the job
  still ends in the right state. The first terminal state wins.
- `FINISHED` only means "an outcome exists". Compliance (compliant, not
  compliant, reach failed…), task errors and "host busy" are in the outcome.
- regops passes appear directly as `FINISHED`.

## Aborting

An abort (from the UI or the API) is appended to the `regency.control`
stream. Runners skip the task if it is still queued (`ABORTED`), or cancel
it cooperatively if it is running: a remediation stops after its current
action, never in the middle of one, and the outcome lists what was done.

## Duplicates

Delivery is at least once: a task can run twice (a runner crashed after
running it, two schedulers fired the same slot). Running twice is harmless
(the second Reach finds the host compliant), and recording is deduplicated
by key: the first outcome recorded wins.
